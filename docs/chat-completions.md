# Schedule assistant Chat Completions contract

`POST /v1/chat/completions` exposes the scheduling assistant through an OpenAI-style envelope, with JSON responses or SSE streaming. It is an application-specific subset, not a general AI proxy.

- Authenticate with `Authorization: Bearer <user access JWT>` from `/api/auth/login`. Never send the provider API key from the browser.
- Send `Content-Type: application/json`, `model: "secretary-schedule"`, and exactly one `messages` entry with `role: "user"` and nonblank text (maximum 4000 characters).
- History is loaded from PostgreSQL for the authenticated account. Client-supplied system/assistant history, multiple choices, arbitrary models, and arbitrary output schemas are rejected. Unsupported request fields return HTTP 400 rather than being silently ignored.
- `GET /v1/models` lists the application model and also requires the user's JWT. The model alias is independent of the actual model configured by `AI_MODEL`.
- `response_format` may be omitted because this assistant always returns structured content. If supplied, use `type: "json_schema"`, `strict: true`, and the exact canonical schema generated by `COMPLETION_RESPONSE_FORMAT` in `app/schemas/chat_completion.py`. A different schema is rejected before calling AI or writing history.

Example request (using the default fixed output schema):

```json
{
  "model": "secretary-schedule",
  "messages": [{"role": "user", "content": "Plan a reading session"}],
  "stream": false
}
```

The response contains `id`, `object: "chat.completion"`, integer Unix `created`, `model`, and one choice with `index: 0`, `finish_reason: "stop"`, and `message.role: "assistant"`. Parse `choices[0].message.content` as JSON to read `answer`, `schedules`, and nullable `proposal`. Usage statistics are omitted because the application cannot accurately infer model token accounting from its transformed response.

Example response:

```json
{
  "id": "chatcmpl-example",
  "object": "chat.completion",
  "created": 1794528000,
  "model": "secretary-schedule",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": "{\"answer\":\"What time should it start?\",\"schedules\":[],\"proposal\":null}",
      "refusal": null
    },
    "finish_reason": "stop",
    "logprobs": null
  }]
}
```

Proposal `proposed_data` is an array of `{ "field": "location", "value": null }` pairs. Only known schedule field names are allowed, and each value is a string or null. This gives strict schemas a bounded set of properties while preserving the difference between an omitted field and an explicit null. The frontend service converts these pairs back into its existing proposal dictionary. Confirmation uses the proposal ID; the server's stored proposal remains authoritative.

Schedule creation/update/cancellation still requires `/api/chat/proposals/{id}/confirm`. Chat history pagination and proposal actions continue to use their existing APIs. The legacy `POST /api/chat/messages` remains available for older clients and returns its original business response shape.

Failures at `/v1/*` use an `error` envelope containing `message`, `type`, `param`, and `code`; status codes include 400 for unsupported/invalid requests, 401 for missing/invalid JWT, 404 for an unknown model, and 502/503 for AI errors/unconfigured AI. No upstream credentials or response bodies are exposed.

The canonical schema is generated from typed response models. When it changes, regenerate the frontend snapshot at `src/contracts/chat-response-format.json` using this command from the backend environment, then run both repositories' contract tests:

```sh
python -c 'import json; from app.schemas.chat_completion import COMPLETION_RESPONSE_FORMAT; print(json.dumps(COMPLETION_RESPONSE_FORMAT, indent=2))'
```

The browser still calls the backend only. The backend independently requests its internal strict schedule-intent schema from CLIProxyAPI, validates ownership and business rules, saves an exchange/proposal, and serializes the result using the public completion schema.

## SSE streaming

Set `stream: true` on the same POST request. The response uses `Content-Type: text/event-stream`, `Cache-Control: no-cache`, and `X-Accel-Buffering: no`. The upstream model is also requested with `stream: true`; the server does not simulate typing after a buffered response.

Each SSE `data:` event contains `object: "chat.completion.chunk"`, a stable completion ID and `choices[0].delta`. Concatenate `delta.content` to obtain the same structured JSON as the nonstreaming content. The first delta has `role: "assistant"`; the final successful chunk has `finish_reason: "stop"`, followed by `data: [DONE]`.

Only the display answer is streamed while the model generates JSON. Schedules and the proposal are appended after complete model output, ownership/business validation and persistence. Treat the partial answer as provisional; never enable proposal confirmation from partial JSON. The frontend reads the POST stream with `fetch` and an incremental UTF-8 decoder, not native `EventSource`.

Authentication, request validation and missing configuration fail with normal HTTP errors before streaming starts. Failures after headers are sent use a safe `data: {"error": ...}` event, without a successful stop chunk or `[DONE]`. EOF alone is not success. Provider responses are bounded to 1 MB and use `AI_TIMEOUT_SECONDS` for socket reads; the frontend aborts after 180 seconds and on component unmount. Closing the chat panel only minimizes it.

Reload history before manually retrying an interrupted request: the server may have committed just before the connection failed. No automatic message retry or schedule mutation occurs. A disconnect before completion closes the upstream generator; cleanup can wait for the current blocking socket read until its configured timeout. Streaming holds one database session per active request. Configure reverse proxies to avoid response buffering and allow the upstream read interval; periodic downstream heartbeat events are not currently implemented.

Tests: `python -m unittest tests.test_chat_stream tests.test_chat_completions -v` covers upstream chunk decoding, escaped Unicode, truncation, error frames, persistence and proposal confirmation.
